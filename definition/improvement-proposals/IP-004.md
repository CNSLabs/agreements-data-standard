# IP-004: Flat Variables, Content Types, Metadata, Schmeas

## Executive Summary

This improvement proposal (IP-004) introduces a standardized approach to variable management, content representation, and metadata handling in the agreements protocol. It defines:

1. A flat variable structure with rich descriptors and validation rules
2. Support for multiple content types with initial focus on MDAST and Markdown
3. Enhanced metadata descriptors for agreement templates
4. JSON schema definitions for validation and generation

These improvements aim to enhance interoperability between protocol logic and client applications while providing a robust foundation for template validation and AI-assisted generation.

## Overview

### Problem Statement

1. **Protocol-Client Interface Limitations**
   * Lack of clear separation between protocol logic and client interfaces
   * Missing variable decorators for improved cross-stack visibility
   * Incomplete validation rule specifications
   * Excessive complexity from nested variable dependencies

2. **Content Format Constraints**
   * Single format support (MDAST only)
   * Limited flexibility for different content representations

3. **Insufficient Metadata Structure**
   * Basic template metadata support
   * Limited contextual information for template processing

4. **Missing Schema Definitions**
   * Absence of formal validation frameworks
   * Lack of machine-readable specifications for tooling

### Proposed Solution

1. **Standardized Variable System**
   * Flat variable structure with comprehensive descriptors
   * Robust validation framework
   * Clean separation of protocol and interface layers

2. **Flexible Content Architecture**
   * Core support for MDAST and Markdown formats
   * Extensible framework for future format integration
   * Unified variable handling across content types

3. **Enhanced Metadata Framework**
   * Rich template identification system

4. **Schema-Driven Validation**
   * Complete JSON schema definitions
   * Machine-friendly specification format

## 1. Flat Variables

The flat variable structure is defined in [`./types/variables.d.ts`](../types/variables.d.ts) and provides a standardized way to define template variables with rich metadata and validation rules.

### Type Definitions

```typescript
type VariableValue = string | number;
type VariableType = string | number | "address" | "dateTime";

interface ValidationRules {
  required?: boolean;
  minLength?: number;
  maxLength?: number;
  pattern?: string;
  min?: number;
  max?: number;
  message?: string;
}

interface Variable {
  id: string;
  type: VariableType; 
  name: string;
  description: string;
  value?: VariableValue;
  defaultValue?: VariableValue;
  validation?: ValidationRules;
}
```

### Template JSON Example

```json
{
  "id": "foundationAddress",
  "type": "address",
  "name": "Foundation Address",
  "description": "Blockchain address of the foundation",
  "value": "0x123f6e75d1BE0ee699C7Eb67594FEbC14ab3AA78",
  "validation": {
    "required": true,
    "pattern": "^0x[a-fA-F0-9]{40}$",
    "message": "Invalid D3 address format"
  }
}
```

### MDAST Interface

Variables can be referenced in MDAST content using the following node structure:

```json
{
  "type": "variable",
  "id": "foundationAddress"
}
```

To reference specific properties of a variable:

```json
{
  "type": "variable",
  "id": "foundationAddress",
  "property": "name"
}
```

### Markdown Interface

In markdown content, variables can be referenced using directives:

```md
:variable{id='foundationAddress'}
:variable{id='foundationAddress' property='name'}
:variable{id='foundationAddress' property='description'}
``` 

## 2. Content Types

The protocol supports multiple content representation formats through a flexible type system defined in [`./types/content.d.ts`](../types/content.d.ts). This allows templates to be authored and processed in different formats while maintaining consistent variable handling and validation.

### Type System

```typescript
type ContentType = 'mdast' | 'md';

interface Content {
  type: ContentType;
  data: MdastNode | MdDoc;
}
```

The current implementation supports two content types:
1. `mdast` - Markdown Abstract Syntax Tree format
2. `md` - Raw markdown text format

Additional content types (e.g. 'mdx', 'blocknote', 'html') can be incrementally added by extending the type system and implementing appropriate parsers and renderers.

### Content Type Examples

#### MDAST Format
```json
{
  "type": "mdast",
  "data": {
    "type": "root",
    "children": [
      {
        "type": "heading",
        "depth": 1,
        "children": [
          {
            "type": "text",
            "value": "Grant Agreement"
          }
        ]
      }
    ]
  }
}
```

#### Markdown Format
```json
{
  "type": "md",
  "data": "# Grant Agreement\n\nThis agreement..."
}
```

The MDAST format provides rich semantic information and easier programmatic manipulation, while the Markdown format offers human-readable authoring experience. Both formats support variable interpolation through their respective syntaxes.

### Schema Validation

Content validation is handled through JSON schemas defined in [`./schema/mdast.schema.json`](../schema/mdast.schema.json) and referenced in the template schema. This ensures structural validity while allowing for format-specific extensions.

## 3. Metadata

Agreement templates include rich metadata defined in [`./types/metadata.d.ts`](../types/metadata.d.ts) to provide context and identification:

```typescript
interface Metadata {
  id: `did:${string}`;
  templateId: `did:template:${string}`;
  version: string;
  createdAt: string;
  name: string;
  author: string;
  description: string;
}
```

### Template JSON example:

```json
{
  "metadata": {
    "id": "did:example:123456789abcdefghi",
    "templateId": "did:template:grant-agreement-v1",
    "version": "1.0.0",
    "createdAt": "2024-03-20T12:00:00Z",
    "name": "Grant Agreement",
    "author": "Ecosystem Name Foundation",
    "description": "Standard grant agreement for ecosystem development funding"
  }
}
```

## 4. JSON Schemas

The protocol defines JSON schemas to enable validation and tooling support. These schemas are located in the [`./schema/`](../schema/) directory:

### Template Schema ([`template.schema.json`](../schema/template.schema.json))

The main schema for agreement templates, defining the structure for:
- Metadata validation
- Variable definitions and constraints
- Content type validation
- Cross-field dependencies

Key sections include:
```json
{
  "type": "object",
  "required": ["metadata", "variables", "content"],
  "properties": {
    "metadata": { "$ref": "#/definitions/metadata" },
    "variables": { 
      "type": "array",
      "items": { "$ref": "#/definitions/variable" }
    },
    "content": {
      "type": "object",
      "required": ["type", "data"],
      "properties": {
        "type": {
          "enum": ["mdast", "md"]
        }
      }
    }
  }
}
```

### MDAST Schema ([`mdast.schema.json`](../schema/mdast.schema.json))

Defines the structure for MDAST content, including:
- Node type definitions
- Child node relationships
- Variable reference validation
- Custom node types for the protocol

The schemas serve multiple purposes:
1. Runtime validation of templates and content
2. Development-time tooling support (IDE integration)
3. Documentation of data structures
4. AI model guidance for template generation
