# IP-006: Object-Based Structure and Enhanced State Machine

## Summary

A significant portion of this proposal will be the enhancement of the execution section, particularly in how inputs and their validation are defined. These enhancements will allow for more flexible and powerful data collection and verification during agreement execution. Included is some simplification of the execution structure, along with more robust indexing into existing portions of the document, with a focus on variables.

### Multi-Value Verifiable Credential Inputs

The new format will support multiple values to be passed in as part of a wrapped EIP-712 signed Verifiable Credential:

```json
"inputs": {
  "partyAData": {
    "type": "VerifiedCredentialEIP712",
    "schema": "verified-credential-eip712.schema.json",
    "displayName": "Party A Signature",
    "description": "EIP712 signature from Party A proposing the terms",
    "data": {
      "partyAName": "${variables.partyAName}",
      "partyBEthAddress": "${variables.partyBEthAddress}"
    },
    "issuer": "${variables.partyAEthAddress.value}"
  }
}
```

In this example, the data field will define multiple values to be collected as part of a single signed submission. These values reference variables defined in the "variables" section of the document, and the validation rules defined there will be used to validate the incoming values.

### Inline Validation Definitions

The proposal will also introduce support for inline definitions of expected input values, without requiring them to be declared in the variables section:

```json
"inputs": {
  "rejected": {
    "type": "VerifiedCredentialEIP712",
    "schema": "verified-credential-eip712.schema.json",
    "displayName": "Party A Rejected Party B's Data",
    "description": "EIP712 signature rejecting the data",
    "data": {
      "partyARejection": {
        "type": "string",
        "validation": {
          "required": true,
          "pattern": "^REJECTED$"
        }
      }
    },
    "issuer": "${variables.partyAEthAddress.value}"
  }
}
```

This approach will allow for defining specialized validation rules for inputs that are only relevant within a specific state transition, without cluttering the main variables section.

### Specific Issuer Requirements

The enhanced format will also support explicitly requiring specific issuers for verifiable credentials:

```json
"issuer": "${variables.partyBEthAddress.value}"
```

This will ensure that only the authorized party can provide the required input.

## Specification

The changes to be introduced in this improvement proposal will involve:

### 1. Object-Based Variables

Variables will be defined as objects with property names as variable IDs, rather than arrays of objects:

**Previous Format:**
```json
"variables": [
  {
    "id": "partyB",
    "type": "string",
    "name": "Party B",
    "description": "Name of the party receiving consulting services",
    "validation": {
      "required": true,
      "minLength": 1
    }
  },
  // Additional variables
]
```

**New Format:**
```json
"variables": {
  "partyAEthAddress": {
    "type": "address",
    "name": "Party A Ethereum Address",
    "description": "Ethereum address of the first party",
    "initiallyRequired": true,
    "validation": {
      "required": true,
      "pattern": "^0x5B38Da6a701c568545dCfcB03FcB875f56beddC4$"
    }
  },
  "partyBName": {
    "type": "string",
    "name": "Party B Name",
    "description": "Legal name of the second party",
    "validation": {
      "required": true,
      "minLength": 1
    }
  }
  // Additional variables
}
```

### 2. Enhanced State Machine

The execution flow will use an object-based state machine with descriptive states:

**Previous Format:**
```json
"execution": {
  "type": "dfsm",
  "data": {
    "states": [
      "AWAITING_SIGNATURES",
      "ACTIVE_PENDING_REVIEW",
      "APPROVED",
      "REJECTED"
    ],
    // Additional properties
  }
}
```

**New Format:**
```json
"execution": {
  "states": {
    "PENDING_PARTY_A_SIGNATURE": {
      "name": "Pending Signature From A",
      "description": "This state awaits until Party A supplies Party B's address along with their own name.",
      "isInitial": true
    },
    "PENDING_PARTY_B_SIGNATURE": {
      "name": "Pending Signature From B",
      "description": "This state awaits until Party B confirms their identity by supplying their name."
    },
    // Additional states
  },
  // Additional properties
}
```

### 3. Simplified Transition Conditions

Transitions will use simpler condition definitions:

**Previous Format:**
```json
"conditions": [
  {
    "type": "isValid",
    "inputs": ["grantRecipientSignature"]
  }
]
```

**New Format:**
```json
"conditions": [
  {
    "type": "isValid",
    "input": "partyAData"
  }
]
```

### 4. Variable References

Input definitions will directly reference variables using the object structure:

**Previous Format:**
```json
"inputs": {
  "grantRecipientSignature": {
    // Properties
    "signer": "${grantRecipientAddress}"
  }
}
```

**New Format:**
```json
"inputs": {
  "partyAData": {
    // Properties
    "data": {
      "partyAName": "${variables.partyAName}",
      "partyBEthAddress": "${variables.partyBEthAddress}"
    },
    "issuer": "${variables.partyAEthAddress.value}"
  }
}
```

### 5. Removing wrapper in execution definition

**Previous Format:**
```json
 "execution": {
      "type": "dfsm",
      "data": {
        "states": [
            ...
```

**New Format:**
```json
    "states": [
        ...
```
