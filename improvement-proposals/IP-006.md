# IP-006: Execution Definition Improvements

## Summary

This improvement proposal (IP-006) introduces significant enhancements to the agreement template structure, focusing on two main areas:

1. Variable organization and validation
2. Execution state machine definition

These changes aim to improve template clarity, reduce redundancy, and provide more robust execution control.

## Overview

### Problem Statement

1. **Variable Structure Limitations**

   * Variables defined as arrays with redundant IDs
   * Validation rules mixed with variable definitions
   * No clear separation between variable definition and usage
2. **Execution Definition Complexity**

   * Overly complex state machine definition with unnecessary type and data wrappers
   * State transitions using arrays of inputs where single input is sufficient
   * Redundant type definitions

### Proposed Solution

## Variable Structure Improvements

### Variable References

Input definitions will directly reference variables using the object structure:

```diff
- "inputs": {
-   "grantRecipientSignature": {
-     // Properties
-     "signer": "${grantRecipientAddress}"
-   }
- }
+ "inputs": {
+   "partyAData": {
+     // Properties
+     "data": {
+       "partyAName": "${variables.partyAName}",
+       "partyBEthAddress": "${variables.partyBEthAddress}"
+     },
+     "issuer": "${variables.partyAEthAddress.value}"
+   }
+ }
```

### Variable References

Variables are referenced in content using template literal syntax:

```json
"${variables.grantRecipientName}"
```

### Multi-Value Verifiable Credential Inputs

The new format will support multiple values to be passed in as part of a wrapped EIP-712 signed Verifiable Credential:

```diff
- "inputs": {
-   "grantRecipientSignature": {
-     "type": "VerifiedCredentialEIP712",
-     "schema": "verified-credential-eip712.schema.json",
-     "displayName": "Party A Signature",
-     "description": "EIP712 signature from Party A proposing the terms",
-     "signer": "${grantRecipientAddress}"
-   }
- }
+ "inputs": {
+   "partyAData": {
+     "type": "VerifiedCredentialEIP712",
+     "schema": "verified-credential-eip712.schema.json",
+     "displayName": "Party A Signature",
+     "description": "EIP712 signature from Party A proposing the terms",
+     "data": {
+       "partyAName": "${variables.partyAName}",
+       "partyBEthAddress": "${variables.partyBEthAddress}"
+     },
+     "issuer": "${variables.partyAEthAddress.value}"
+   }
+ }
```

In this example, the data field will define multiple values to be collected as part of a single signed submission. These values reference variables defined in the "variables" section of the document, and the validation rules defined there will be used to validate the incoming values.

### Inline Validation Definitions

The proposal will also introduce support for inline definitions of expected input values, without requiring them to be declared in the variables section:

```diff
- "inputs": {
-   "rejected": {
-     "type": "VerifiedCredentialEIP712",
-     "schema": "verified-credential-eip712.schema.json",
-     "displayName": "Party A Rejected Party B's Data",
-     "description": "EIP712 signature rejecting the data",
-     "signer": "${grantRecipientAddress}"
-   }
- }
+ "inputs": {
+   "rejected": {
+     "type": "VerifiedCredentialEIP712",
+     "schema": "verified-credential-eip712.schema.json",
+     "displayName": "Party A Rejected Party B's Data",
+     "description": "EIP712 signature rejecting the data",
+     "data": {
+       "partyARejection": {
+         "type": "string",
+         "validation": {
+           "pattern": "^REJECTED$"
+         }
+       }
+     },
+     "issuer": "${variables.partyAEthAddress.value}"
+   }
+ }
```

This approach will allow for defining specialized validation rules for inputs that are only relevant within a specific state transition, without cluttering the main variables section.

### Specific Issuer Requirements

The enhanced format will also support explicitly requiring specific issuers for verifiable credentials:

```diff
- "issuer": "${grantRecipientAddress}"
+ "issuer": "${variables.partyBEthAddress.value}"
```

This will ensure that only the authorized party can provide the required input.

### Object-Based Variables

Variables are now defined as objects with property names as variable IDs, removing redundancy and improving clarity:

```diff
- "variables": [
-   {
-     "id": "partyB",
-     "type": "string",
-     "name": "Party B",
-     "description": "Name of the party receiving consulting services",
-     "validation": {
-       "required": true,
-       "minLength": 1
-     }
-   }
- ]
+ "variables": {
+   "partyB": {
+     "type": "string",
+     "name": "Party B",
+     "description": "Name of the party receiving consulting services",
+     "validation": {
+       "required": true,
+       "minLength": 1
+     }
+   }
+ }
```

Key changes:

- Variables defined as object properties instead of array items
- Removed redundant `id` field (using object key as identifier)
- Cleaner validation rule structure

## Execution Definition Improvements

### Updated State Definitions

The execution definition is a bit cleaner and states now have a bit more information:

```diff
- "execution": {
-   "type": "dfsm",
-   "data": {
-     "states": [
-       "AWAITING_SIGNATURES",
-       "ACTIVE_PENDING_REVIEW",
-       "APPROVED",
-       "REJECTED"
-     ]
-   }
- }
+ "execution": {
+   "states": {
+     "AWAITING_TEMPLATE_VARIABLES": {
+       "name": "Awaiting Template Variables",
+       "description": "Grantor needs to fill out the template variables."
+     },
+     "AWAITING_RECIPIENT_SIGNATURE": {
+       "name": "Pending Recipient Signature",
+       "description": "This state awaits until Recipient signing the agreement."
+     }
+   }
+ }
```

Key changes:

- Removed `type` and `data` wrapper (type is implied)
- States defined as objects with metadata
- Each state has a name and description

### State Transitions

State transitions maintain their condition-based structure but with improved clarity:

```diff
- "transitions": [
-   {
-     "from": "AWAITING_SIGNATURES",
-     "to": "ACTIVE_PENDING_REVIEW",
-     "conditions": [
-       {
-         "type": "isValid",
-         "inputs": ["grantRecipientSignature"]
-       }
-     ]
-   }
- ]
+ "transitions": [
+   {
+     "from": "AWAITING_TEMPLATE_VARIABLES",
+     "to": "AWAITING_RECIPIENT_SIGNATURE",
+     "conditions": [
+       {
+         "type": "isValid",
-         "inputs": ["grantRecipientSignature"]
+         "input": "grantorData"
+       }
+     ]
+   }
+ ]
```

Key changes:

- Single input per condition (instead of array of inputs)
