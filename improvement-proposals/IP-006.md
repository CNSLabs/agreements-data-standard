# IP-006: Object-Based Structure and Enhanced State Machine

## Summary

This improvement proposal will introduce significant structural enhancements to the Agreements Data Standard, upgrading from the array-based definitions to object-based structures. These changes will improve readability, maintainability, and provide richer descriptive capabilities for templates and state machines.

## Enhanced Execution Input Definitions

A major improvement in this proposal will be the enhancement of the execution section, particularly in how inputs and their validation are defined. These enhancements will allow for more flexible and powerful data collection and verification during agreement execution.

### Multi-Value Verifiable Credential Inputs

The new format will support multiple values to be passed in as part of a wrapped EIP-712 signed Verifiable Credential:

```json
"inputs": {
  "partyAData": {
    "type": "VerifiedCredentialEIP712",
    "schema": "verified-credential-eip712.schema.json",
    "displayName": "Party A Signature",
    "description": "EIP712 signature from Party A proposing the terms",
    "data": {
      "partyAName": "${variables.partyAName}",
      "partyBEthAddress": "${variables.partyBEthAddress}"
    },
    "issuer": "${variables.partyAEthAddress.value}"
  }
}
```

In this example, the data field will define multiple values to be collected as part of a single signed submission. These values reference variables defined in the "variables" section of the document, and the validation rules defined there will be used to validate the incoming values.

### Inline Validation Definitions

The proposal will also introduce support for inline definitions of expected input values, without requiring them to be declared in the variables section:

```json
"inputs": {
  "rejected": {
    "type": "VerifiedCredentialEIP712",
    "schema": "verified-credential-eip712.schema.json",
    "displayName": "Party A Rejected Party B's Data",
    "description": "EIP712 signature rejecting the data",
    "data": {
      "partyARejection": {
        "type": "string",
        "validation": {
          "required": true,
          "pattern": "^REJECTED$"
        }
      }
    },
    "issuer": "${variables.partyAEthAddress.value}"
  }
}
```

This approach will allow for defining specialized validation rules for inputs that are only relevant within a specific state transition, without cluttering the main variables section.

### Specific Issuer Requirements

The enhanced format will also support explicitly requiring specific issuers for verifiable credentials:

```json
"issuer": "${variables.partyBEthAddress.value}"
```

This will ensure that only the authorized party can provide the required input.

## Specification

The changes to be introduced in this improvement proposal will involve:

### 1. Object-Based Variables

Variables will be defined as objects with property names as variable IDs, rather than arrays of objects:

**Previous Format:**
```json
"variables": [
  {
    "id": "partyB",
    "type": "string",
    "name": "Party B",
    "description": "Name of the party receiving consulting services",
    "validation": {
      "required": true,
      "minLength": 1
    }
  },
  // Additional variables
]
```

**New Format:**
```json
"variables": {
  "partyAEthAddress": {
    "type": "address",
    "name": "Party A Ethereum Address",
    "description": "Ethereum address of the first party",
    "initiallyRequired": true,
    "validation": {
      "required": true,
      "pattern": "^0x5B38Da6a701c568545dCfcB03FcB875f56beddC4$"
    }
  },
  "partyBName": {
    "type": "string",
    "name": "Party B Name",
    "description": "Legal name of the second party",
    "validation": {
      "required": true,
      "minLength": 1
    }
  }
  // Additional variables
}
```

### 2. Enhanced State Machine

The execution flow will use an object-based state machine with descriptive states:

**Previous Format:**
```json
"execution": {
  "type": "dfsm",
  "data": {
    "states": [
      "AWAITING_SIGNATURES",
      "ACTIVE_PENDING_REVIEW",
      "APPROVED",
      "REJECTED"
    ],
    // Additional properties
  }
}
```

**New Format:**
```json
"execution": {
  "states": {
    "PENDING_PARTY_A_SIGNATURE": {
      "name": "Pending Signature From A",
      "description": "This state awaits until Party A supplies Party B's address along with their own name.",
      "isInitial": true
    },
    "PENDING_PARTY_B_SIGNATURE": {
      "name": "Pending Signature From B",
      "description": "This state awaits until Party B confirms their identity by supplying their name."
    },
    // Additional states
  },
  // Additional properties
}
```

### 3. Simplified Transition Conditions

Transitions will use simpler condition definitions:

**Previous Format:**
```json
"conditions": [
  {
    "type": "isValid",
    "inputs": ["grantRecipientSignature"]
  }
]
```

**New Format:**
```json
"conditions": [
  {
    "type": "isValid",
    "input": "partyAData"
  }
]
```

### 4. Direct Variable References

Input definitions will directly reference variables using the object structure:

**Previous Format:**
```json
"inputs": {
  "grantRecipientSignature": {
    // Properties
    "signer": "${grantRecipientAddress}"
  }
}
```

**New Format:**
```json
"inputs": {
  "partyAData": {
    // Properties
    "data": {
      "partyAName": "${variables.partyAName}",
      "partyBEthAddress": "${variables.partyBEthAddress}"
    },
    "issuer": "${variables.partyAEthAddress.value}"
  }
}
```

## Benefits

The proposed enhancements will offer numerous advantages for template developers and end-users:

### Structural Improvements
1. **Intuitive Object Access**: Object-based structures will provide more intuitive direct access by property names instead of array indices
2. **Clear Separation of Concerns**: Template definition and initialization parameters will be clearly separated
3. **Self-Documenting Code**: The descriptive format will make templates more self-documenting and easier to understand

### State Machine Enhancements
4. **Rich State Description**: States will include names, descriptions, and explicit initial state indicators
5. **Explicit State Transitions**: Transitions will be clearer with direct reference to single inputs
6. **Visual Representation**: Enhanced state definitions will enable better visualization of agreement flows

### Advanced Input Capabilities
7. **Multi-Value Submissions**: Support for collecting multiple values in a single signed credential
8. **Flexible Validation**: Inline validation definitions for specialized input requirements
9. **Targeted Validation Rules**: Input-specific validation rules without cluttering the variables section
10. **Authorized Signers**: Explicit issuer requirements to ensure only authorized parties can provide inputs

### Developer Experience
11. **Simplified References**: More straightforward variable references using the object structure
12. **Reduced Redundancy**: Less repetition of common structures and patterns
13. **Better Maintainability**: Enhanced structure will make templates easier to maintain and update

### End-User Experience
14. **Clearer Agreement Flows**: Better state descriptions will make agreement progression more transparent
15. **More Precise Validation**: Enhanced validation capabilities will reduce errors in agreement execution

## Backwards Compatibility

The key functional behaviors of the data standard will remain unchanged, including:
- Variable interpolation in content
- State machine transitions based on verifiable inputs
- Markdown and MDAST content support
- EIP-712 signature verification

## Implementation

The reference implementation will be found in the templates directory, which will demonstrate a complete Memorandum of Understanding (MOU) agreement using the new format.

## Conclusion

The object-based structure to be introduced in this proposal will significantly enhance the Agreements Data Standard, making it more intuitive, descriptive, and maintainable. The new format will provide a solid foundation for future extensions while retaining the core capabilities that make the standard powerful for blockchain-based agreements.
