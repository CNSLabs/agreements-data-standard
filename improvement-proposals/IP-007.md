# IP-007: Variable Groups

## Executive Summary

This improvement proposal (IP-007) introduces a lightweight grouping mechanism for variables in the Agreements protocol. It defines:

1. A flexible variable grouping system with single-level nesting
2. Standardized group reference syntax

These improvements aim to enhance variable organization while maintaining flexibility and avoiding premature domain-specific constraints.

## Overview

### Problem Statement

1. **Variable Organization Limitations**
   * Flat variable structure lacks organizational capabilities
   * No standardized way to group related variables
   * Missing semantic context for variable collections
   * Potential for inconsistent variable naming across templates

2. **Domain-Specific Constraints**
   * Early adoption of opinionated groupings (e.g., "contracts", "identities")
   * Special case processing required in execution engines
   * Limited flexibility for emerging use cases
   * Potential lock-in to specific domain models

### Proposed Solution

1. **Lightweight Grouping System**
   * Single-level variable nesting
   * Flexible, user-defined group names
   * Standardized reference syntax

## 1. Variable Groups

The variable group structure provides a standardized way to organize related variables while maintaining flexibility and avoiding premature domain-specific constraints.

### Basic Structure

Variables can be organized into groups using a simple nested structure, where each group is an object with type, name, description, and contents properties:

```json
{
  "variables": {
    "contracts": {
      "type": "group",
      "name": "Smart Contracts",
      "description": "Smart contract related variables",
      "contents": {
        "grantContract": {
          "type": "address",
          "name": "Grant Contract",
          "description": "Address of the grant contract"
        },
        "tokenContract": {
          "type": "address",
          "name": "Token Contract",
          "description": "Address of the token contract"
        }
      }
    },
    "identities": {
      "type": "group",
      "name": "Participant Identities",
      "description": "Addresses and identities of agreement participants",
      "contents": {
        "grantor": {
          "type": "address",
          "name": "Grantor",
          "description": "Address of the grantor"
        }
      }
    }
  }
}
```

### Reference Syntax

Variables must be referenced using template literal syntax:

```
${variables.contracts.grantContract}
```

This format ensures consistent variable interpolation across all content types and makes it clear when a variable is being referenced.

### Markdown Content

In markdown content, variables are referenced using the template literal syntax:

```md
# Grant Agreement

The grant contract address is ${variables.contracts.grantContract}

## Participants

Grantor: ${variables.identities.grantor}
```

## 2. Implementation Considerations

### Benefits

1. **Flexibility**
   * User-defined groups emerge naturally
   * No premature domain-specific constraints
   * Adaptable to various use cases

2. **Simplicity**
   * Single-level nesting keeps complexity low
   * Clear reference syntax
   * Minimal special case processing

### Limitations

1. **Domain Knowledge**
   * No built-in domain-specific optimizations
   * Requires explicit group definitions
   * May need additional tooling for common patterns

2. **Complexity Trade-offs**
   * Single-level nesting may be limiting for some use cases
   * Additional syntax for group references
   * Potential for inconsistent group naming

## 3. Migration Path

Existing templates can be migrated to the new group system by:

1. Identifying related variables
2. Creating appropriate groups
3. Moving variables into groups
4. Updating references in content

Example migration:

```json
// Before
{
  "variables": {
    "grantContract": {
      "type": "address"
    },
    "tokenContract": {
      "type": "address"
    }
  }
}

// After
{
  "variables": {
    "contracts": {
      "type": "group",
      "name": "Smart Contracts",
      "description": "Smart contract related variables",
      "contents": {
        "grantContract": {
          "type": "address"
        },
        "tokenContract": {
          "type": "address"
        }
      }
    }
  }
}
```

## 4. Additional Improvement Ideas

The following features could be considered for future improvements:

1. **Root-Level Variable Access**
   * Optional flag to enable referencing variables without the `variables.` prefix
   * Example: `contracts.grantContract` instead of `variables.contracts.grantContract`
   * Requires careful consideration of naming conflicts

2. **Group Metadata and Domain Context**
   * Optional metadata for groups to provide domain-specific context
   * Domain type hints (e.g., "contracts", "identities", "financial", "legal")
   * Semantic categorization for client applications
   * Example:
     ```json
     {
       "contracts": {
         "type": "group",
         "name": "Smart Contracts",
         "description": "Smart contract related variables",
         "domain": {
           "type": "contracts",
           "category": "blockchain",
           "subcategory": "ethereum",
           "purpose": "contract_reference"
         },
         "contents": {
           "grantContract": { ... }
         }
       }
     }
     ```
   * This approach allows clients to:
     * Understand the semantic context of the group
     * Apply appropriate domain-specific validation
     * Choose appropriate representation based on their needs
     * Maintain flexibility in how the information is presented

3. **Multi-level Group Nesting**
   * Support for nested groups in future versions
   * Example structure:
     ```json
     {
       "variables": {
         "contracts": {
           "type": "group",
           "name": "Smart Contracts",
           "contents": {
             "token": {
               "type": "group",
               "name": "Token Contracts",
               "contents": {
                 "grant": {
                   "type": "group",
                   "name": "Grant Contracts",
                   "contents": {
                     "address": { ... }
                   }
                 }
               }
             }
           }
         }
       }
     }
     ```
   * Considerations:
     * Impact on reference syntax
     * Complexity vs. flexibility trade-offs
     * Migration path from single-level nesting
     * Client application support

4. **Group Inheritance and Composition**
   * Reusable group definitions
   * Template composition
   * Group specialization
   * Validation rules at group level

5. **Client Tooling**
   * Group visualization components
   * Group management interfaces
   * Template migration tools
   * Group-aware editors
