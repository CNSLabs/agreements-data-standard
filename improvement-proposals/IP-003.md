# IP-003: Standardizing Transaction Proof Fields in the Agreements Protocol

## Executive Summary

This proposal introduces a clear, standardized structure for transaction proofs within the agreements protocol. By defining required and optional fields in a JSON-based format, we ensure consistent verification of on-chain actions across agreement types and improve interoperability between systems.

## Problem Statement

Currently, transaction proofs lack a standardized structure. This leads to inconsistent implementations and potential verification issues when validating on-chain actions.

## Proposed Solution

We propose an addition to the JSON data standard for transaction proofs, specifying required and optional fields for each transaction type. This approach:

- Ensures compatibility with different EVM chains
- Supports various proof verification methods
- Provides clear validation rules for each field

## Transaction Metadata Structure

Transaction metadata and proof definition is a JSON object with fields that vary based on the transaction type. Below are the standardized formats for the two main transaction types.

### 1. Native Token Transfer

**Example:**
```json
{
  "transactionType": "nativeTransfer",
  "from": "0xSenderAddress",
  "to": "0xRecipientAddress",
  "value": "1000000000000000000", // Amount in wei
  "chainId": 1,
}
```

**Field Requirements:**
- `transactionType` (string, required): Must be `"nativeTransfer"`
- `from` (string, required): Sender address
- `to` (string, required): Recipient address
- `value` (string, required): Amount transferred (in wei)
- `chainId` (number, required): Chain ID where the transaction occurred

### 2. Contract Method Call

**Example:**
```json
{
  "transactionType": "contractCall",
  "contractAddress": "0xContractAddress",
  "method": "transfer",
  "params": { 
    // Keys must match the parameter names as defined in the contract's ABI for this method
    "to": "0xRecipientAddress",
    "amount": "1000000000000000000"
  },
  "contractReference": "${contracts.erc20-mainnet}",
  "signer": "0xSignerAddress",
  "chainId": 1,
}
```

**Field Requirements:**
- `transactionType` (string, required): Must be `"contractCall"`
- `contractAddress` (string, required): Address of the contract
- `method` (string, required): Contract method called
- `params` (object, required): Parameters passed to the method. Keys must match the parameter names as defined in the referenced contract's ABI for this method
- `contractReference` (string, required): Reference to contract definition using dot notation (see Contract Definitions below)
- `signer` (string, optional): Address of the transaction signer

## Contract Definitions

To support multiple proofs referencing the same contract, contract definitions are separated into their own section. Transaction metadata of type contract call can reference contracts by their `id`.

**Example:**
```json
{
  "id": "erc20-mainnet",
  "name": "Mainnet ERC20 Token",
  "description": "Standard ERC20 token contract on Ethereum mainnet",
  "address": "0xContractAddress",
  "chainId": 1,
  "abi": [ /* ... ABI array ... */ ]
}
```

**Field Requirements:**
- `id` (string, required): Unique identifier for the contract
- `name` (string, optional): Display name
- `description` (string, optional): Description
- `address` (string, required): Contract address
- `chainId` (number, required): Chain ID
- `abi` (array, required): Contract ABI for decoding transaction data

## Data Standard Changes

### 1. Transaction Hash Variable

A new variable type, `txHash`, is introduced. It includes metadata describing the expected transaction type and proof requirements desscribed above.

**TypeScript Example:**
```ts
interface TxHashVariable {
  type: "txHash";
  txMetadata: TxMetadata;
  // ... other fields ...
}

type TxMetadata = NativeTransferDetails | ContractCallDetails;

interface NativeTransferDetails {
  transactionType: "nativeTransfer";
  from: string;
  to: string;
  value: string; // in wei
  chainId: number;
}

interface ContractCallDetails {
  transactionType: "contractCall";
  method: string;
  params: Record<string, any>;
  contractReference: string;
  signer?: string;
}
```

### 2. Contract Definition Section

Contracts are defined separately and referenced by `contractReference` in proofs.

**TypeScript Example:**
```ts
interface Contract {
  id: string;
  name?: string;
  description?: string;
  address: string;
  chainId: number;
  abi: any[];
}
```

## Full JSON Example

This example demonstrates how the agreements protocol standardizes transaction proof requirements using a structured JSON format. In this scenario, the execution machine expects an input called `workTokenSentTx`, which is a `txHash` variable. This variable must reference a transaction where the address `0x67fD5A5ec681b1208308813a2B3A0DD431Be7278` (the signer) sends 100 tokens to `0xBe32388C134a952cdBCc5673E93d46FfD8b85065` by calling the `transfer` method on the ERC20 contract defined as `workToken`. The `workToken` contract is specified in the `contracts` section, including its address, chain ID (Linea Sepolia, chainId: 59141), and ABI. This structure ensures that the transaction proof is both verifiable and unambiguous, enabling reliable validation of on-chain actions within the protocol.

```json
{
  "variables": {
    "workTokenSentTx": { // Defining a txHash variable
      "type": "txHash",
      "name": "Transaction Hash",
      "validation": {
        "required": true
      },
      "txMetadata": { // Metadata describing the contract call for the corresponding transaction
        "transactionType": "contractCall",
        "method": "transfer",
        "params": {
          "to": "0xBe32388C134a952cdBCc5673E93d46FfD8b85065",
          "value": 100
        },
        "contractReference": "${contracts.workToken}", // Referencing workToken contract in contracts section
        "signer": "0x67fD5A5ec681b1208308813a2B3A0DD431Be7278"
      }
    }
  },
  "contracts": {
    "workToken": { // Defining the workToken contract
      "description": "The Work Token",
      "address": "0x12be78ca652191616f49420dfa28214bafe9326c",
      "chainId": "59141",
      "abi": "...ABI..."
    }
  },
  "execution": {
    "inputs": {
      "workTokenSentTx": {
        "type": "VerifiedCredentialEIP712",
        "schema": "verified-credential-eip712.schema.json",
        "displayName": "Work Approved and Payment Proof",
        "description": "Grantor confirms work has been accepted and payment has been sent.",
        "data": {
           "workTokenSentTx": "${variables.workTokenSentTx}" // Referencing the workTokenSentTx txHash variable
        },
        "issuer": "${variables.grantorEthAddress.value}"
      }
    }
    // state machine definition ...
  }
}
```

## Conclusion

Standardizing transaction proof requirements with a clear JSON schema ensures reliable verification of on-chain actions within the agreements protocol. This approach provides a robust, extensible structure for transaction proofs and contract references, supporting future growth and interoperability.
