# IP-003: Enhancing the agreements protocol by clearly defining required fields for transaction proofs 

## Executive Summary

This proposal aims to standardize the structure and required fields for transaction proofs within the agreements protocol. By establishing clear requirements for transaction proof inputs, we can ensure consistent verification of on-chain actions across different agreement types while maintaining interoperability between systems.

## Overview

### Problem Statement

Currently, transaction proofs lack standardized field requirements, leading to inconsistent implementation across different agreements and potential verification issues when validating on-chain actions.

### Proposed Solution

Define a comprehensive set of required and optional fields for transaction proofs that:
- Maintains compatibility with different EVM chains
- Supports various proof verification methods
- Provides clear validation rules for each field

### Transaction Type-Specific Fields

Additional fields required based on transaction type:

#### 1. Native Token Transfer

| Field | Type | Description | Required |
| --- | --- | --- | --- |
| `transactionType` | `string` | Must be "nativeTransfer" | ✅ |
| `from` | `string` | Sender address | ✅ |
| `to` | `string` | Recipient address | ✅ |
| `value` | `string` | Amount transferred (in wei) | ✅ |
| `chainId` | `number` | Chain ID where the transaction was sent | ✅ |

#### 2. Contract Method Call

| Field | Type | Description | Required |
| --- | --- | --- | --- |
| `transactionType` | `string` | Must be "contractCall" | ✅ |
| `contractAddress` | `string` | Address of the contract interacted with | ✅ |
| `method` | `string` | Contract method called | ✅ |
| `params` | `object` | Parameters passed to the method | ✅ |
| `contractReference` | `string` | Reference to contract definition | ✅ |
| `signer` | `string` | Address of the signer of the transaction | ✅ |

### Contract Definition

To support multiple proofs referencing the same contract, contract definitions can be separated out into their own section in the data standard. This way they can be referenced wherever needed.

| Field | Type | Description | Required |
| --- | --- | --- | --- |
| `id` | `string` | Unique identifier for the contract | ✅ |
| `name` | `string` | Display name of the contract | ❌ |
| `description` | `string` | Description of the contract | ❌ |
| `address` | `string` | Contract address | ✅ |
| `chainId` | `number` | Chain ID where contract is deployed | ✅ |
| `abi` | `array` | Contract ABI for decoding transaction data | ✅ |

## Data Standard Changes

1. **TxHash Variable Type + Transaction Metadata** - Specifies a new variable describing allowing the input of a transaction hash and a proof. Each TxHash variable also includes TxMetadata that specifies what type of transaction the variable expects, and thus what proof is required.

```tsx
interface TxHashVariable {
  type: "txHash";
  txMetadata: TxMetadata;
  // Other fields for generic variable
  // ...
}

// Core proof components
interface TxMetadata = NativeTransferDetails | ContractCallDetails

// Used to define the details of a native token transfer transaction
interface NativeTransferDetails {
  transactionType: "nativeTransfer";
  from: string;
  to: string;
  value: number; // in wei
  chainId: number;
}

// Used to define the details of a contract method call transaction
interface ContractCallDetails {
  transactionType: "contractCall";
  method: string;
  params: Record<string, any>;
  contractReference?: string; // Reference to a contract definition by id
}
```

2. **Contract Definition** - A new section for defining contracts. This is used to support multiple proofs referencing the same contract, and a section for referencing contracts in contract prose.

```tsx
// Core proof components
interface Contract {
  name: string;
  description: string;
  address: string;
  chainId: number;
  abi: string;
}
```

## Conclusion

Standardizing transaction proof requirements ensures reliable verification of on-chain actions within the agreements protocol. This proposal provides a clear structure for defining transaction proofs while maintaining flexibility for different verification methods.
