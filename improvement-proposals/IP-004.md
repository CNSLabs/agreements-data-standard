# IP-004: Flat Variables, Content Types, Metadata, Schemas

## Executive Summary

This improvement proposal (IP-004) introduces a standardized approach to variable management, content representation, and metadata handling in the agreements standard. It defines:

1. A flat variable structure with rich descriptors and validation rules
2. Support for multiple content types with initial focus on MDAST and Markdown
3. Enhanced metadata descriptors for agreement templates
4. JSON schema definitions for validation and generation

These improvements aim to enhance interoperability between the standard model and client applications while providing a robust foundation for template validation and AI-assisted generation.

## Overview

### Problem Statement

1. **Standard-Client Interface Limitations**
   * Lack of clear separation between the standard model and client interfaces
   * Missing variable decorators for improved cross-stack visibility
   * Incomplete validation rule specifications
   * Excessive complexity from nested variable dependencies

2. **Content Format Constraints**
   * Single format support (MDAST only)
   * Limited flexibility for different content representations

3. **Insufficient Metadata Structure**
   * Basic template metadata support
   * Limited contextual information for template processing

4. **Missing Schema Definitions**
   * Absence of formal validation frameworks
   * Lack of machine-readable specifications for tooling

### Proposed Solution

1. **Standardized Variable System**
   * Flat variable structure with comprehensive descriptors
   * Robust validation framework
   * Clean separation of standard and interface layers

2. **Flexible Content Architecture**
   * Core support for MDAST and Markdown formats
   * Extensible framework for future format integration
   * Unified variable handling across content types

3. **Enhanced Metadata Framework**
   * Rich template identification system

4. **Schema-Driven Validation**
   * Complete JSON schema definitions
   * Machine-friendly specification format

## 1. Flat Variables

The flat variable structure provides a standardized way to define template variables with rich metadata and validation rules.

### Schema Definition

```json
{
  "variables": {
    "type": "array",
    "items": {
      "type": "object",
      "required": ["id", "type", "name", "description"],
      "properties": {
        "id": {
          "type": "string",
          "description": "Unique identifier for the variable"
        },
        "type": {
          "type": "string",
          "enum": ["string", "number", "address", "dateTime"],
          "description": "Data type of the variable"
        },
        "name": {
          "type": "string",
          "description": "Human-readable name for the variable"
        },
        "description": {
          "type": "string",
          "description": "Detailed description of the variable's purpose"
        },
        "value": {
          "oneOf": [
            { "type": "string" },
            { "type": "number" }
          ],
          "description": "Current value of the variable"
        },
        "defaultValue": {
          "oneOf": [
            { "type": "string" },
            { "type": "number" }
          ],
          "description": "Default value if none is provided"
        },
        "validation": {
          "type": "object",
          "properties": {
            "required": { "type": "boolean" },
            "minLength": { "type": "number" },
            "maxLength": { "type": "number" },
            "pattern": { "type": "string", "format": "regex" },
            "min": { "type": "number" },
            "max": { "type": "number" },
            "message": { "type": "string" }
          }
        }
      }
    }
  }
}
```

**Note**: Validation rules based on HTML5 form validation attributes. Refer to [MDN's Form Validation](https://developer.mozilla.org/en-US/docs/Learn/HTML/Forms/Form_validation).


### Template JSON Example

```json
{
  "id": "foundationAddress",
  "type": "address",
  "name": "Foundation Address",
  "description": "Blockchain address of the foundation",
  "value": "0x123f6e75d1BE0ee699C7Eb67594FEbC14ab3AA78",
  "validation": {
    "required": true,
    "pattern": "^0x[a-fA-F0-9]{40}$",
    "message": "Invalid D3 address format"
  }
}
```

### MDAST Interface

Variables can be referenced in MDAST content using the following node structure:

```json
{
  "type": "variable",
  "id": "foundationAddress"
}
```

To reference specific properties of a variable:

```json
{
  "type": "variable",
  "id": "foundationAddress",
  "property": "name"
}
```

### Markdown Interface

In markdown content, variables can be referenced using directives:

```md
:variable{id='foundationAddress'}
:variable{id='foundationAddress' property='name'}
:variable{id='foundationAddress' property='description'}
``` 

## 2. Content Types

The standard supports multiple content representation formats through a flexible type system. This allows templates to be authored and processed in different formats while maintaining consistent variable handling and validation.

### Schema Definition

```json
{
  "content": {
    "type": "object",
    "required": ["type", "data"],
    "properties": {
      "type": {
        "type": "string",
        "enum": ["mdast", "md"],
        "description": "Content format type"
      },
      "data": {
        "oneOf": [
          {
            "if": { "properties": { "type": { "const": "mdast" } } },
            "then": { "$ref": "mdast.schema.json" }
          },
          {
            "if": { "properties": { "type": { "const": "md" } } },
            "then": { "type": "string" }
          }
        ]
      }
    }
  }
}
```

The current implementation supports two content types:
1. `mdast` - Markdown Abstract Syntax Tree format
2. `md` - Raw markdown text format

Additional content types (e.g. 'mdx', 'blocknote', 'html') can be incrementally added by extending the schema and implementing appropriate parsers and renderers.

### Content Type Examples

#### MDAST Format
```json
{
  "type": "mdast",
  "data": {
    "type": "root",
    "children": [
      {
        "type": "heading",
        "depth": 1,
        "children": [
          {
            "type": "text",
            "value": "Grant Agreement"
          }
        ]
      }
    ]
  }
}
```

#### Markdown Format
```json
{
  "type": "md",
  "data": "# Grant Agreement\n\nThis agreement..."
}
```

The MDAST format provides rich semantic information and easier programmatic manipulation, while the Markdown format offers human-readable authoring experience. Both formats support variable interpolation through their respective syntaxes.

## 3. Metadata

Agreement templates include rich metadata to provide context and identification:

### Schema Definition

```json
{
  "metadata": {
    "type": "object",
    "required": ["id", "templateId", "version", "createdAt", "name", "author", "description"],
    "properties": {
      "id": {
        "type": "string",
        "pattern": "^did:.*",
        "description": "Unique identifier for the agreement instance"
      },
      "templateId": {
        "type": "string",
        "pattern": "^did:template:.*",
        "description": "Identifier for the template type"
      },
      "version": {
        "type": "string",
        "description": "Semantic version of the template"
      },
      "createdAt": {
        "type": "string",
        "format": "date-time",
        "description": "Creation timestamp"
      },
      "name": {
        "type": "string",
        "description": "Human-readable template name"
      },
      "author": {
        "type": "string",
        "description": "Template author or organization"
      },
      "description": {
        "type": "string",
        "description": "Detailed template description"
      }
    }
  }
}
```

### Template JSON example:

```json
{
  "metadata": {
    "id": "did:example:123456789abcdefghi",
    "templateId": "did:template:grant-agreement-v1",
    "version": "1.0.0",
    "createdAt": "2024-03-20T12:00:00Z",
    "name": "Grant Agreement",
    "author": "Ecosystem Name Foundation",
    "description": "Standard grant agreement for ecosystem development funding"
  }
}
```

## 4. JSON Schemas

The standard defines JSON schemas to enable validation and tooling support. These schemas are located in the `./schema/` directory:

### Template Schema (`template.schema.json`)

The main schema for agreement templates, defining the structure for:
- Metadata validation
- Variable definitions and constraints
- Content type validation
- Cross-field dependencies

Key sections include:
```json
{
  "type": "object",
  "required": ["metadata", "variables", "content"],
  "properties": {
    "metadata": { "$ref": "#/definitions/metadata" },
    "variables": { 
      "type": "array",
      "items": { "$ref": "#/definitions/variable" }
    },
    "content": {
      "type": "object",
      "required": ["type", "data"],
      "properties": {
        "type": {
          "enum": ["mdast", "md"]
        }
      }
    }
  }
}
```

### MDAST Schema (`mdast.schema.json`)

Defines the structure for MDAST content, including:
- Node type definitions
- Child node relationships
- Variable reference validation
- Custom node types for the standard

The schemas serve multiple purposes:
1. Runtime validation of templates and content
2. Development-time tooling support (IDE integration)
3. Documentation of data structures
4. AI model guidance for template generation

## Other Considerations

### Variable References in Execution Flow

While the `executionFlow` structure is being actively developed, variables can be referenced using JSON template syntax: `${variableId}`. When no property is specified, the reference defaults to accessing the variable's `value` property.

For accessing other properties, dot notation can be used: `${variableId.propertyName}`.

Example from a grant agreement execution flow:
```json
{
  "states": ["DRAFT", "AWAITING_SIGNATURES", "PAYMENT_PENDING", "COMPLETED"],
  "transitions": [
    {
      "from": "PAYMENT_PENDING",
      "to": "COMPLETED",
      "conditions": [
        {
          "type": "transactionVerified",
          "params": {
            "recipient": "${foundationAddress}",
            "recipientName": "${foundationAddress.name}",
            "amount": "${grantAmount}",
            "deadline": "${termEndDate}"
          }
        }
      ]
    }
  ]
}
```

This reference syntax provides a unified way to access variables and their properties in both content and execution contexts, maintaining consistency across all formats while the specific structure of `executionFlow` continues to evolve.

### Future Improvements

As we continue developing the standard, this IP should serve as a helpful reference point for adding new features such as state-machine and proofs. The flat variable structure, content type system, and schema definitions provide a solid foundation that we can build upon.
